# Feature: 工作流暂停态持久化（等待输入的会话在 Worker 重启后可续跑）

> **本文档定位 — 纯 What（需求口径，不随代码漂移）**
>
> spec 只回答 **做什么 / 验收标准 / 不做什么**。所有 How（决策、数据流、字段、API、Service、前端、文件清单、性能指标）一律不写在这里，How 的唯一真相在 design.md 与 tasks.md。

**关联 PRD**: 无（缺陷修复；来源：workflow-study 联调复现，`questions.md` Q6）
**优先级**: P0
**所属版本**: v3.1.0
**依赖**: 无
**状态**: 草稿，待用户确认（2026-11-25）。Spec Discovery 已与用户对齐：修复思路为“暂停时持久化、续跑时重建”；保留期默认 7 天且可配置；升级前已暂停的会话不保证可续跑；走完整 SDD 流程。

> **范围边界**
> - **本次纳入**：
>   - 工作流在“等待用户输入”处暂停时，持久化续跑所需的运行状态。
>   - 平台对话（WebSocket）与开放 API（`/api/v2/workflow/invoke`）两个续跑入口同时受益。
>   - 暂停状态的保留期（默认 7 天，运维可配置）、到期后的明确报错、结束后的清理。
>   - 暂停中的会话被用户停止时，不依赖原 Worker。
> - **本次明确排除**：
>   - **运行中（RUNNING）被中断的工作流**的恢复：Worker 在节点执行过程中崩溃，属于另一类问题，另起 feature。
>   - **每一步的检查点与节点级重试**：本期只在“等待输入”这一种暂停点持久化。
>   - **升级前已经暂停的会话**：升级后仍按现状失败，不做迁移。
>   - **工作流语义变更**：节点行为、校验规则、事件格式均不改。
>   - **暂停态内容的查看与管理界面**：不提供。

## 1. 用户故事

作为 **使用对话式工作流的终端用户**，
我希望 **在流程停下来等我输入时，即使系统在这期间重启或升级，我回来继续输入仍能接着往下跑**，
以便 **不必从头重新开始，也不会丢失之前已经填写和生成的内容**。

作为 **通过开放 API 调用工作流的集成方**，
我希望 **暂停的会话可以由任意一个 Worker 续跑，而不是必须回到同一个进程**，
以便 **我的系统可以放心做滚动升级和扩缩容**。

作为 **平台运维人员**，
我希望 **暂停态有明确的保留期且结束后自动清理**，
以便 **控制存储占用，并能在会话过期时给出可理解的原因**。

---

## 2. 验收标准

### 2.1 持久化与续跑

- **AC-01** — WHEN 工作流运行到“等待用户输入”的节点并暂停, THE SYSTEM SHALL 保存续跑所需的全部运行状态，使该会话不再依赖任何单个 Worker 进程的内存。
- **AC-02** — WHEN 用户对已暂停的会话提交输入，且最初暂停该会话的 Worker 进程已经重启或被替换, THE SYSTEM SHALL 从暂停的节点继续执行，结果与进程不重启时一致。
- **AC-03** — WHEN 会话续跑, THE SYSTEM SHALL 让后续节点能读取暂停之前已产生的数据，包括各节点的输出、全局变量与本次运行内的对话历史。
- **AC-04** — WHEN 同一次运行多次暂停（例如循环对话）, THE SYSTEM SHALL 在每一次暂停之后都可以续跑，包括每次之间发生进程重启的情形。
- **AC-05** — THE SYSTEM SHALL 对平台对话与开放 API 两个入口给出一致的续跑结果。
- **AC-06** — WHEN 会话暂停后工作流的定义被编辑、保存或上线了新版本, THE SYSTEM SHALL 仍按该会话启动时的定义续跑，不受新版本影响。

### 2.2 保留期与清理

- **AC-07** — THE SYSTEM SHALL 把暂停态保留 7 天，保留期可由运维通过配置调整。
- **AC-08** — IF 用户在保留期之后的一天之内提交输入, THEN THE SYSTEM SHALL 把会话置为失败，并返回一个明确表示“会话已过期”的错误，而不是笼统的“对象不存在”；超过这一天后，该会话号等同于未知会话，按现有机制处理（2026-11-25 用户确认的修订：原文未限定时间，实现上提示窗口为保留期后一天）。
- **AC-09** — WHEN 工作流运行成功、失败或被停止, THE SYSTEM SHALL 删除该会话已持久化的暂停态。
- **AC-10** — WHEN 用户停止一个已暂停的会话, THE SYSTEM SHALL 在不依赖原 Worker 的情况下结束该会话，并删除其暂停态。

### 2.3 异常、并发与安全

- **AC-11** — IF 已持久化的暂停态无法还原（内容损坏、与当前代码版本不兼容）, THEN THE SYSTEM SHALL 把会话置为失败并给出可读原因，不得使请求挂起。
- **AC-12** — WHEN 同一个暂停点同时收到两次输入, THE SYSTEM SHALL 只让其中一次续跑，不得重复执行后续节点；对外的拒绝沿用现有机制：WebSocket 返回错误码 10543，开放 API 返回只含 `close` 事件的空流（2026-11-25 用户确认的修订：原文要求“另一次返回明确的拒绝”，开放 API 上现状不满足，按现状记录）。
- **AC-13** — THE SYSTEM SHALL 保持租户与工作流隔离：只有同一租户下、同一工作流的请求才能续跑该会话，不匹配时拒绝（与现状一致）。
- **AC-14** — THE SYSTEM SHALL NOT 在日志中输出暂停态的内容原文（用户输入、节点输出、变量值）。
- **AC-15** — WHEN 升级前已经暂停的会话在升级后被续跑, THE SYSTEM SHALL 保持现状行为（失败并返回现有错误），不得因此阻塞其他会话。

---

## 3. 边界情况

- 暂停期间 Redis 不可用时，续跑请求应返回明确的服务不可用错误，而不是误报“会话已过期”。
- 暂停态很大（长对话历史、大量变量）时，应有明确的上限与超限行为（对外表现为暂停时失败并给出原因，而不是静默丢失）；上限数值在 design.md 定。
- 用户在保留期的最后时刻提交输入时，以提交那一刻是否过期为准。
- 多个 Worker 同时存在时，续跑可落在任意一个；原有的按会话固定 Worker 的做法是否保留，由 design.md 决定，对外行为不变。
