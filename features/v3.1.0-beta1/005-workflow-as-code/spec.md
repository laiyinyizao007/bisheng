# 工作流即代码（YAML 声明 + CLI 命令族 + 节点模板后端化）

> **本文档定位 — 纯 What（需求口径，不随代码漂移）**
>
> spec 只回答 **做什么 / 验收标准 / 不做什么**。所有 How（决策、数据流、字段、API、Service、前端、文件清单、性能指标）一律不写在这里，How 的唯一真相在 [design.md](./design.md) 与 [tasks.md](./tasks.md)。

**版本**：v3.1.0-beta1。**优先级**：P1。**状态**：待用户确认（2026-11-20 编写）。

**关联需求**：本会话已确认的范围与形态决策——落点在毕昇 fork 本地仓库先自用；入口形态为给**已有的 `bisheng` CLI** 增加一条 `flow` 命令族（不新造 CLI）；声明形式为 YAML 唯一真相源 + 收窄的 Python 覆盖层；节点模板从前端常量搬到后端并经接口发布；写路径需要一个专用权限位与对应的开放接口面；diff 默认对比线上当前版本、可选历史版本；push 总是新建版本；Python 覆盖层保留但做窄。

**依赖**：F053（`bisheng` CLI 包与其凭据 / 客户端 / 输出 / 退出码设施）、F049/F053（开放 API 凭据底座与权限位机制）、既有工作流与版本模型、既有工作流引擎。

> **范围边界**
>
> - **本次纳入**：
>   - **节点模板后端化**：节点模板由后端持有并经接口发布；前端节点库与知识库问答助手快捷建流两处消费点改为从接口取；工具节点模板由后端统一生成。
>   - **CLI `flow compile`**：YAML 声明 + 收窄的 Python 覆盖层 → 毕昇工作流定义；编译期结构校验；提示词可外置为独立文件。
>   - **CLI `flow diff`**：本地编译结果与线上版本的结构化差异——逐节点、逐参数、逐连线，机器可读。
>   - **CLI `flow push`**：新建一个工作流版本；推送前强制展示线上独有内容；不覆盖既有版本。
>   - **CLI `flow run`**：经开放接口调起工作流，处理等待输入节点的暂停与续跑。
>   - **CLI `flow tool`**：由 OpenAPI 描述注册自定义工具，并列出可用工具供工作流声明引用。
>   - **工作流写操作面**：承载工作流创建、版本新建、版本读取、工具注册与工具列表的开放接口，配一个专用权限位。
> - **本次明确排除**：
>   - **覆盖既有版本 / 原地改写线上工作流**（push 总是新建版本）——避免"整份覆盖静默吞掉线上改动"这一正是本特性要根治的问题在本特性自身重现。
>   - **自动上线 / 自动发布工作流**（上线仍是人工动作；本特性只到"版本已建立"为止）。
>   - **绕过人工的批准机制**（本特性不引入任何"模型代替人确认"的通道）。
>   - **任意文件读写、任意命令执行**——CLI 权限面不因本特性扩大。
>   - **工作流定义的可视化编辑**（本特性只提供声明式定义面，不改网页画布的编辑交互）。
>   - **工作流运行时语义的变更**（节点行为、图编译规则、迭代上限等均不改动）。
>   - **非 Python 的声明式形式**（本版只有 YAML）。

## 1. 用户故事

作为 **工作流开发者**，
我希望 **用一份 YAML 声明工作流、由命令行编译成毕昇能用的定义、推送前看清与线上版本的每一处差异、推送后能用同一条命令跑起来调试**，
以便 **工作流的定义进入版本管理、与代码一起评审与回滚，不再靠"仓库里的脚本"与"线上那条工作流"两处真相靠人手对齐**。

作为 **本地 coding agent**，
我希望 **编译、差异、推送、运行四类命令在无 TTY 下可跑通、输出可被机器解析、失败时能拿到"缺什么、怎么改"而不是堆栈**，
以便 **自主完成"改 YAML → 看差异 → 推送 → 跑一次看结果"的闭环，不必在中间环节等人接手机器人**。

作为 **平台管理员**，
我希望 **节点模板只有一份真相且由后端持有、前端与命令行工具同源消费**，
以便 **节点定义变更时不会出现"界面是一套、命令行是另一套"的漂移**。

## 2. 验收标准

> AC 编号在本特性内唯一。括号内标注不变量或既有行为来源。错误码仅作"可观测的对外行为"引用，定义与归属写在 design.md。

### 2.1 节点模板后端化

- **AC-01** — THE SYSTEM SHALL 由后端持有并经一个只读接口发布工作流节点模板，接口返回全部 12 类节点（start / input / output / llm / agent / qa_retriever / rag / knowledge_retriever / report / code / condition / end）的模板定义；THE SYSTEM SHALL NOT 在前端再保留第二份节点模板常量。
- **AC-02** — WHEN 前端节点库与知识库问答助手快捷建流两处取节点模板，THE SYSTEM SHALL 两者经同一接口取得同一份数据；两处的节点渲染与既有行为一致。
- **AC-03** — THE SYSTEM SHALL 在模板中只发布结构与参数键，不发布界面文案；界面文案仍由前端本地化资源提供。THE SYSTEM SHALL NOT 因模板接口而引入任何界面语言依赖。
- **AC-04** — THE SYSTEM SHALL 由后端统一生成工具节点的模板（工具参数与输出两组的形状），前端与命令行工具消费同一份生成结果；THE SYSTEM SHALL NOT 存在"前端一份生成逻辑、命令行一份复刻"的双份实现。
- **AC-05** — IF 模板接口不可用或返回失败，THEN THE SYSTEM SHALL 令依赖模板的界面操作失败并给出可读原因；THE SYSTEM SHALL NOT 回落到任何硬编码的模板副本。

### 2.2 声明式定义与编译

- **AC-06** — WHEN 开发者提供一份符合声明格式的 YAML，THE SYSTEM SHALL 编译出毕昇工作流定义（节点、连线、画布视图三部分），且编译结果与开发者声明的节点类型、参数、连线关系一致。
- **AC-07** — THE SYSTEM SHALL 支持在 YAML 中把提示词等长文本外置为独立文件并按引用展开；THE SYSTEM SHALL NOT 要求长文本内联在 YAML 里。
- **AC-08** — WHEN 开发者提供 YAML 与一份 Python 覆盖层，THE SYSTEM SHALL 只允许该覆盖层**覆盖 YAML 已声明节点的已声明参数**、以及**追加 YAML 未声明的节点与连线**；IF 覆盖层试图删除或改变 YAML 已声明的节点与连线结构，THEN THE SYSTEM SHALL 拒绝并说明被拒的具体项。
- **AC-09** — THE SYSTEM SHALL 保证 YAML 是工作流定义的唯一真相源：同一份 YAML 在不同环境编译出的定义一致，除开发者显式声明的环境差异外不得有隐式差异。
- **AC-10** — IF 声明文件无法安全解析（例如含可执行对象标签），THEN THE SYSTEM SHALL 拒绝该文件并说明原因；THE SYSTEM SHALL NOT 以任何方式执行声明文件中的内容。
- **AC-11** — IF 声明文件缺少必填的顶层字段或顶层不是键值映射，THEN THE SYSTEM SHALL 在本地即拒绝并指出缺失项，不发起任何平台请求。

### 2.3 编译期结构校验

- **AC-12** — IF 编译结果缺少起始节点，THE SYSTEM SHALL 拒绝并说明缺少起始节点。
- **AC-13** — IF 编译结果中某个非终止节点没有任何连线，THE SYSTEM SHALL 拒绝并指出该节点。
- **AC-14** — IF 编译结果引用了平台不存在的节点类型，THE SYSTEM SHALL 拒绝并指出该类型。
- **AC-15** — IF 某类节点缺少其运行所必需的参数，THE SYSTEM SHALL 拒绝并指出该节点与缺失的参数名。
- **AC-16** — IF 编译结果中的变量引用格式不被平台识别，THE SYSTEM SHALL 拒绝并指出该引用；THE SYSTEM SHALL NOT 让格式错误的引用进入平台——平台对不识别的引用是静默不替换的。
- **AC-17** — IF 某条连线指向不存在的节点，或其来源句柄不是该节点声明的分支，THEN THE SYSTEM SHALL 拒绝并指出该连线。
- **AC-18** — WHEN 编译结果通过上述全部校验，THE SYSTEM SHALL 报告校验通过并产出可推送的定义；THE SYSTEM SHALL NOT 在校验未覆盖的结构上做额外拦截。

### 2.4 与线上版本的差异

- **AC-19** — WHEN 开发者要求对比线上工作流与本地定义，THE SYSTEM SHALL 产出一份结构化差异，至少区分：线上独有的节点、本地独有的节点、同一节点上取值不同的参数、线上独有的连线、本地独有的连线。
- **AC-20** — THE SYSTEM SHALL 在差异中给出每个差异项的可定位信息（节点标识、参数键、连线两端与句柄），使开发者能据此定位到具体改动。
- **AC-21** — THE SYSTEM SHALL NOT 把画布坐标、画布视图与界面排布类信息计为差异——它们不影响工作流的执行语义。
- **AC-22** — WHEN 开发者指定对比某个历史版本，THE SYSTEM SHALL 以该版本为基准产出差异；WHEN 未指定，THE SYSTEM SHALL 以线上当前版本为基准。
- **AC-23** — THE SYSTEM SHALL 以机器可读形式输出差异，使本地 agent 能据此自行判断与修改；人读呈现与机器可读呈现的差异内容一致。
- **AC-24** — IF 线上工作流不存在、无权读取或读取失败，THEN THE SYSTEM SHALL 明确区分这三种情形并各自给出可行动的原因，THE SYSTEM SHALL NOT 报告"无差异"。

### 2.5 推送

- **AC-25** — WHEN 开发者推送一份通过校验的本地定义，THE SYSTEM SHALL 为目标工作流**新建**一个版本承载该定义；THE SYSTEM SHALL NOT 覆盖或改写任何既有版本。
- **AC-26** — WHEN 推送前存在线上独有的节点、连线或参数取值，THE SYSTEM SHALL 先展示这些将被保留在旧版本中的内容；IF 开发者未显式确认覆盖，THEN THE SYSTEM SHALL 拒绝推送。
- **AC-27** — IF 目标工作流处于上线状态且平台不允许对其建立新版本，THEN THE SYSTEM SHALL 明确报告该状态并给出可行动的下一步（如下线），THE SYSTEM SHALL NOT 报告推送成功。
- **AC-28** — IF 推送所需的凭据不具备写工作流的权限，THEN THE SYSTEM SHALL 明确报告权限不足并指出缺少的权限位，THE SYSTEM SHALL NOT 退化为只读操作或静默跳过。
- **AC-29** — WHEN 推送成功，THE SYSTEM SHALL 报告新建版本的标识与版本名，使开发者能据此在平台界面上定位该版本。

### 2.6 运行与调试

- **AC-30** — WHEN 开发者请求运行一个工作流，THE SYSTEM SHALL 经平台开放的调用面发起运行，并把运行事件流呈现出来。
- **AC-31** — WHEN 运行停在等待输入的节点，THE SYSTEM SHALL 报告停在哪个节点与等待什么输入，并接受开发者提供的输入后继续本次运行；THE SYSTEM SHALL 在继续时同时携带本次运行的会话标识与被等待的那条消息标识。
- **AC-32** — IF 运行中某个节点失败，THE SYSTEM SHALL 报告失败节点与失败原因，不得只报告运行结束。
- **AC-33** — WHEN 开发者提供一次性输入（供 agent 或脚本调用），THE SYSTEM SHALL 能在无 TTY 下完成"运行到下一次等待输入"的全过程；THE SYSTEM SHALL NOT 在无 TTY 时阻塞等待人工输入。

### 2.7 工具注册

- **AC-34** — WHEN 开发者提供一份 OpenAPI 描述，THE SYSTEM SHALL 据其注册平台自定义工具，并使描述中的每个操作成为该工具类型下的一个可用操作。
- **AC-35** — WHEN 注册完成，THE SYSTEM SHALL 报告工具类型标识与各可用操作的标识，使工作流声明能按操作标识引用它们。
- **AC-36** — WHEN 开发者列出可用工具，THE SYSTEM SHALL 报告各工具类型及其可用操作。
- **AC-37** — IF 工具注册所需的凭据不具备注册权限，THEN THE SYSTEM SHALL 明确报告权限不足，THE SYSTEM SHALL NOT 报告注册成功。

### 2.8 权限与边界

- **AC-38** — THE SYSTEM SHALL 承载工作流写操作的凭据须持有一个专用于写工作流的权限位；THE SYSTEM SHALL NOT 以任何其他权限位替代它放行写操作。
- **AC-39** — WHERE 多租户启用，THE SYSTEM SHALL 保持租户隔离与既有资源动作权限；持写工作流权限位的凭据仍不得越权改动它无权的工作流。
- **AC-40** — IF 权限评估不可用、评估失败或结果不可判定，THEN THE SYSTEM SHALL 拒绝该操作，THE SYSTEM SHALL NOT 以"无差异""已跳过"或任何部分结果放行。
- **AC-41** — THE SYSTEM SHALL NOT 在任何输出、异常信息与本地日志中回显凭据明文。
- **AC-42** — THE SYSTEM SHALL NOT 为工作流写操作新增任何"指定他人身份"的入口；写操作以凭据自身的资源归属人身份进行。
- **AC-43** — IF 凭据未绑定资源归属人，THEN THE SYSTEM SHALL 拒绝该操作并明确指出缺少归属人；THE SYSTEM SHALL NOT 把"无归属人"当作对任何工作流都有权。
- **AC-44** — THE SYSTEM SHALL 以平台侧为工作流声明格式的权威定义方；命令行工具所持的声明格式定义 SHALL 与平台侧同源，THE SYSTEM SHALL NOT 存在两份各自演化的声明格式定义。声明格式变更时，平台侧与命令行工具 SHALL 在同一次变更中一起更新。

## 3. 边界情况

- 当工作流定义中引用的工具尚未注册时，编译应报出该引用不可解析，而不是产出一个缺 `tool_key` 的节点。
- 当工作流定义用到报告节点时，其报告模板引用是平台侧的资源标识，不能由声明凭空生成；处理方式见 design.md。
- 当同一份声明在两个不同平台上编译时，节点模板可能因平台版本不同而存在差异；差异应体现在编译结果中，而不是被静默抹平。
- 当线上工作流处于运行中时，推送建立新版本不影响在途运行；版本切换的时机由开发者决定。
- 当差异中出现仅参数取值不同、而该参数在平台上不参与执行时，仍按差异报出——平台是否使用某参数是平台的事，差异工具不替它判断。
- 当工具注册使用的 OpenAPI 描述缺少操作标识时，注册应失败并说明缺少哪一项，因为操作标识是工作流引用工具的唯一依据。
