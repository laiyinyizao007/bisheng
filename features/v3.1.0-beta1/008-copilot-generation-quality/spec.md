# 工作流 copilot 生成质量（先问再做、说清做不到、评测集）

> **本文档定位 — 纯 What（需求口径，不随代码漂移）**
>
> spec 只回答 **做什么 / 验收标准 / 不做什么**。所有 How（提示词、事件、解析、前端组件、评测脚本、文件清单）一律不写在这里，How 的唯一真相在 [design.md](./design.md) 与 [tasks.md](./tasks.md)。

**版本**：v3.1.0-beta1。**优先级**：P1。**状态**：2026-11-25 用户已确认（AC-11 门槛按建议值）。

**背景（试用证据）**：用 F007 copilot 生成「报销助手」后，输入「报销claude code 500$ 研发用」结果不对，三处问题都不在平台，而在生成：
1. 需求没提币种，copilot 没发现，把 500$ 当 500 元处理，输出写死「元」；
2. 「大于 500 走审批」按不含 500 处理，500 不触发审批，且没有告诉用户这个取舍；
3. 需求说「审批」，平台没有审批节点，copilot 悄悄降级成一句提示，既没说明做不到，也没用现成的「发送邮件 / 飞书 / 钉钉」工具。

**关联需求**：本会话已确认的 Spec Discovery 决策（brainstorming，2026-11-25）——
- **模糊需求**：影响结果正确性的关键点没说清时**先问再做**，问题带选项；需求清楚时直接出方案，不打扰。
- **澄清的形式**：回答里给出可点选的问题卡片，选完一键作为下一轮发出；作答后卡片锁定、只读显示所选答案。
- **衡量方式**：建一套评测集，对真实模型自动跑；先跑现状基线，改完再跑对比。
- **路线**：先做「单次调用 + 需求清单 + 能力边界 + 澄清卡片」（方案 A），按评测数据再决定是否拆成「先分析后生成」两步（方案 B）或加「样例走查自检」（方案 C）。
- **落点**：独立特性 F008，叠在 F007 之上；评测用隔离环境的「工作流默认模型」（当前 MiniMax-M3）。

**依赖**：F007-workflow-copilot（抽屉、对话、方案预览与应用、推理显示、结构校验与重试）；F006「工作流声明」技能包；平台既有节点模板、工具列表与代码节点开关。

> **范围边界**
>
> - **本次纳入**：
>   - **先问再做**：关键点没说清时，copilot 用带选项的问题卡片先澄清，再出方案。
>   - **写明假设**：次要细节由 copilot 自行取默认值，并在方案说明里逐条列出。
>   - **说清做不到**：需求用到平台没有的能力时，明确说明哪部分做不到，并给出平台上最接近的替代做法。
>   - **评测集与评测脚本**：可重复运行、给出分项得分，用于证明改动的效果。
> - **本次明确排除**：
>   - **新增平台能力**：不新增审批节点、定时触发、数据库读写等节点；只让 copilot 正确说明并给出替代。
>   - **F007 已确认的行为变化**：先预览后应用、对话不落库、使用工作流默认模型、结构校验与重试、推理显示，一律不变。
>   - **把评测放进 CI**：评测调用真实模型、产生费用，只手动运行。
>   - **方案 B / C 的实现**：本期只做方案 A；B / C 是否需要、何时做，由评测结果决定，另行确认。

## 1. 用户故事

作为 **工作流搭建者**，
我希望 **在我漏说关键细节（币种、边界、审批怎么发起）时，copilot 先用几个点选题问清楚**，
以便 **得到的工作流在真实输入下就是对的，而不是看起来完整、一跑就错**。

作为 **工作流搭建者**，
我希望 **copilot 遇到平台做不到的事时直接告诉我，并给出能做的替代**，
以便 **不会误以为「审批」已经实现，结果只是一句提示**。

作为 **copilot 的维护者**，
我希望 **有一套能反复运行的评测，给出分项得分**，
以便 **每次改提示词都知道是变好还是变坏，而不是凭一两次手试下结论**。

## 2. 验收标准

### 2.1 先问再做

- **AC-01** — WHEN 用户的需求在以下任一方面没说清、且对话中此前也没有回答过：单位 / 币种 / 格式，数值边界是否包含，异常或空输入怎么处理，循环何时结束，会产生副作用的动作（通知、审批、写入数据）具体怎么做, AND 这一点会影响结果是否正确或会触发副作用, THE SYSTEM SHALL 先回复澄清问题而不给出方案：最多 3 个问题，每题 2–4 个选项，并允许「其他」自由填写；本轮画布不变。
- **AC-02** — WHEN 用户的需求没有上述关键缺口, THE SYSTEM SHALL 直接给出方案，不追问。
- **AC-03** — THE SYSTEM SHALL 把澄清问题显示为回复中的卡片：每题可点选一个选项，或选「其他」并填写文字；全部作答后才可点「按这些继续」；点下后把各题答案作为下一条用户消息发出（在对话中可见），下一轮据此生成。
- **AC-04** — WHEN 卡片已提交, THE SYSTEM SHALL 将卡片锁定为只读，显示每题所选答案；WHEN 用户未作答而直接发送了新消息, THE SYSTEM SHALL 将该卡片锁定为「未作答」。改答案只能通过新消息。

### 2.2 写明假设、说清做不到

- **AC-05** — WHEN 给出方案, THE SYSTEM SHALL 在方案说明中逐条列出 copilot 自行决定的次要细节（例如「『大于 500』不含 500」）；没有假设时不列。
- **AC-06** — WHEN 需求用到平台当前没有的能力（例如审批、定时触发、数据库读写、HTTP 请求，以及被关闭的代码节点）, THE SYSTEM SHALL 在回复中明确说明哪部分做不到，并在当前用户可用的资源中给出最接近的替代（例如用「发送邮件」工具通知审批人）；SHALL NOT 不加说明地降级实现。若此点本身影响做法，按 AC-01 先问。
- **AC-07** — THE SYSTEM SHALL 依据平台**当前**的节点类型、代码节点开关和当前用户可用的工具判断「做不到」与「替代」，不依据固定写死的清单。

### 2.3 评测集

- **AC-08** — THE SYSTEM SHALL 提供不少于 15 条评测用例，覆盖四组：需求清楚应直接做、有隐含缺口应先问、平台做不到应说明、修改已有画布；每条写明应问及的要点、方案必须满足的硬性要求、以及若干样例输入及其应有结果。
- **AC-09** — THE SYSTEM SHALL 提供评测脚本，对配置好的环境中的「工作流默认模型」逐条运行（每条至少运行 2 次），输出每条与汇总的四项指标：该问时问了 / 不该问时没问、方案通过结构校验、硬性要求满足、样例走查正确；样例走查由评判模型给出结论并记录理由，供人工抽查。应问的用例在问后由脚本按用例给定的答案自动作答，再评估随后的方案。
- **AC-10** — THE SYSTEM SHALL 在修改 copilot 之前先对现状运行评测并留存基线结果；修改后再次运行并与基线对比留存。评测不进入 CI，输出与留存的结果中不含密钥、令牌或连接信息。
- **AC-11** — 方案 A 视为达标的门槛（2026-11-25 用户确认）：「应先问」组的提问命中率 ≥ 80%；「应直接做」组的误问率 ≤ 20%；「做不到」组明确说明的比例 ≥ 75%；结构校验通过率不低于基线。未达标时由用户决定继续调整或启用方案 B / C。

### 2.4 不变

- **AC-12** — THE SYSTEM SHALL 保持 F007 的既有行为不变：先预览后应用、可撤销、不自动保存、对话不落库、使用工作流默认模型、结构校验与最多 3 次重试、推理显示。

## 3. 边界情况

| 情况 | 期望 |
|---|---|
| 模型把问题写成普通文字而不是卡片 | 照常作为文字显示；评测中计为「格式未遵守」 |
| 一次回答里既有问题又有方案 | 以方案为准；问题部分作为文字显示，不出卡片 |
| 问题超过 3 个或选项不足 2 个 | design 阶段定裁剪或降级为文字的规则 |
| 用户对卡片选「其他」但没填文字 | 视为未作答，「按这些继续」不可点 |
| 用户在卡片提交后又改主意 | 发新消息说明；旧卡片保持锁定 |
| 澄清后用户的回答又引出新的关键缺口 | 可以再问一轮，仍受每轮最多 3 题的限制 |
| 评测运行中模型超时或报错 | 该次运行计为失败并记录原因，不中断其余用例 |
